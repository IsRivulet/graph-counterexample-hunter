# 课程项目：Skill 端到端 Benchmark 执行方案

## 目标

验证 `graph-counterexample-hunter` Skill 是否能帮助模型更可靠地发现并报告有限简单无向图命题的反例，同时记录它带来的时间和 token 成本。

## 1. 冻结测试案例

项目已有两套可复用材料：

- `cases.json` / `expectations.json`：10 条公开开发样例，适合先跑通流程和评分器，不作为最终泛化成绩。
- `../MathCheck_E2E_TestSet_v1/MathCheck_E2E_TestSet_v1/MathCheck_E2E_Bench_v1.json`：42 条端到端案例，覆盖命题解析、搜索范围与模式、澄清/不支持输入、候选核验与缩小、后端故障处理。
- `formal_v1/`：转换器已将其中 39 条可由真实模型直接运行的用例转换成当前执行器格式；另外 3 条需故障注入，记录在 `formal_v1/exclusions.json`，不进入普通 live run。

建议课程项目以 39 条可运行用例为主集；若执行成本受限，可先选 24 条分层子集：12 条存在反例、6 条范围内无反例、3 条候选图核验、3 条澄清或不支持。按案例家族分组后再划分开发/评测，近似命题及同一候选图变体必须放在同一组，避免相似题泄漏。

在第一次正式运行前冻结题目、答案、分组和评分规则，并保存文件哈希。若其中案例已用于反复修改 Skill，就把它们标为开发集；另从未用于调试的命题家族留出至少 12 条作为期末报告中的 held-out 小测试集。held-out 题目和答案在两组运行结束前不要查看或修改。

每条案例至少记录：案例 ID、类别、难度、用户原始输入、正确命题/范围、是否存在反例、参考反例或标准核验结果。可接受任意有效反例，不要求边列表与参考图完全相同。转换脚本保留题目原始文本和候选图夹具，答案单独保存在 expectations 文件。

## 2. 对反例成功与质量评分

### 成功判定

对“反例存在”案例，只有独立 oracle 确认图结构合法、处于指定范围、满足全部前提且结论为假，才记为找到反例。否则记失败。对无反例案例，按题目要求确认穷举覆盖；随机/特殊搜索没有命中只能算预算内未找到，不能当作证明。

核心结果：

- **反例召回率** = 找到有效反例的反例存在案例数 / 反例存在案例总数。
- **反例精确率** = 有效反例数 / 所有声称找到反例的案例数。
- **误报率** = 无反例案例中错误声称找到反例的数量 / 无反例案例总数。

### 质量评分

反例有效性是门槛：无效反例质量记 0。有效反例再由两名评审在不知道运行组别的情况下评分；如只有一名评审，至少对全部反例盲评并在报告注明。

| 维度 | 评分 | 判定 |
|---|---:|---|
| 规模与简洁性 | 0–2 | 0：反例有效但在指定范围内存在明显更小反例，系统未缩小也未说明；1：有效，且有范围内最少顶点证据或相对原候选已缩小，但边数最小性未证明；2：oracle 确认在指定范围内顶点数最少，并在该顶点数下边数最少。 |
| 数学解释 | 0–2 | 0：未说明为何构成反例或解释错误；1：指出前提成立、结论失败但证据不完整；2：逐项解释前提与结论的真假，并与图结构证据一致。 |
| 证据与表述 | 0–2 | 0：无核验或夸大结论；1：给出核验结果但范围/最小性边界不清；2：明确范围、搜索模式、核验和缩小复核结果，未把有限搜索包装成一般证明。 |

报告三项均分及总分（0–6），同时单列有效反例率。不要把“反例更小”并入“是否发现反例”，两者分别报告。

## 3. 做公平的成对对照

每条输入分别运行两次。当前 `run.py` 的 `--condition` 已支持两组：

- **Skill 组**：启用当前冻结版本的 Skill。
- **基线组**：同一模型、相同工具和后端，只提供用户输入，不加载该 Skill 的说明。

示例命令（两次必须使用相同的案例集、模型和 timeout）：

```powershell
python benchmark/skill_e2e/run.py --cases benchmark/skill_e2e/formal_v1/cases.json --condition skill --model gpt-6-luna --output benchmark/skill_e2e/runs/course-skill
python benchmark/skill_e2e/run.py --cases benchmark/skill_e2e/formal_v1/cases.json --condition baseline --model gpt-6-luna --output benchmark/skill_e2e/runs/course-baseline
python benchmark/skill_e2e/score.py --run benchmark/skill_e2e/runs/course-skill --expectations benchmark/skill_e2e/formal_v1/expectations.json
python benchmark/skill_e2e/score.py --run benchmark/skill_e2e/runs/course-baseline --expectations benchmark/skill_e2e/formal_v1/expectations.json
```

先用同一组 2–3 个 ID 做小规模预跑，确认 CLI 能完成并产生日志；之后再跑全量或同一批分层子集。执行器每题会复制后端工作区，模型输入可能较大：已有两题试跑记录的输入 token 分别约 96k 和 169k，因此先估算额度/成本，避免一开始就跑 39 条双组全量。

固定模型、模型配置、后端版本、超时和运行环境。每个案例使用全新会话；随机决定两组的运行先后次序。随机搜索案例按固定种子至少重复 3 次；其他案例至少运行 1 次。完整保留失败和超时，不能只挑成功或最快的一次。

运行前记录 Skill 文件、后端目录、题集与答案文件的版本或 SHA-256。记录模型请求名称与日期；模型请求名称不能当作服务端精确版本证明。

## 4. 记录效率与成本

逐案例记录以下字段：

| 字段 | 说明 |
|---|---|
| `condition` | `skill` 或 `baseline` |
| `case_id`, `repeat_id` | 案例和重复运行编号 |
| `valid_counterexample` | oracle 核验后的有效性 |
| `wall_time_seconds` | 从提交到最终响应的总时间 |
| `input_tokens`, `output_tokens` | 执行器提供时记录；缺失填空，不估算 |
| `backend_calls` | 搜索、核验、缩小分别计数及总数 |
| `graphs_examined` | 后端实际检查数；不可用时留空 |
| `timeout_or_error` | 超时或失败的原始状态 |
| `quality_*` | 盲评质量分 |

比较两组全部案例的中位耗时、P95 耗时、中位输入/输出 token、超时率和后端调用数。另报告“成功找到有效反例案例”的条件耗时和 token，但不要只报告成功案例成本；失败和超时也应计入总体效率。

## 5. 结果分析与课程报告

主表按 Skill / 基线并排列出：反例召回率、反例精确率、误报率、质量三项均分、中位及 P95 耗时、中位 token、超时率。再按题型分层列出结果，避免整体均值掩盖某类问题。

建议重点回答：

1. Skill 是否提高有效反例发现率？差异来自哪些题型？
2. Skill 是否减少无效反例或过度声称？
3. 反例质量是否更好，尤其是缩小和解释？
4. 提升需要多少额外时间、token 和后端调用？
5. held-out 小测试上的趋势是否与开发集一致？样本较少时只做描述性结论，不声称统计显著或普遍泛化。

至少附 3 个逐题案例：Skill 明显成功、两组都成功但质量/成本不同、Skill 失败或误报。报告题集版本、样本数、模型/配置、运行日期、失败数和评审方式。

## 执行顺序

1. 先用 10 条公开样例确认执行与评分流程可用。
2. 冻结 39 条可运行正式题集和 held-out 分组，保留 3 条故障注入用例作为后续扩展；补齐参考答案及每题的反例存在性。
3. 完成盲评评分表和逐题运行日志。
4. 运行 Skill/基线成对对照并保留全部 trace。
5. 评分、汇总效率与质量指标，再撰写结论。

真实模型运行会消耗模型额度；正式 39 条双组运行前，建议先用 2–3 条案例确认 CLI、登录状态和日志目录正常，再启动全量运行。
